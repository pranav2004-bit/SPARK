## The Problem

**Substantially revised during this file's second audit (2026-09-20) — the true scope is much larger than the first two drafts described.** The first drafts characterized this as a single, isolated ~12-second incident. Checking PgBouncer's full retained log history instead of just the window around one test shows this is wrong:

- **64,062 "server login has been failing" warnings across the last 6 days** (2026-09-15 through 2026-09-20) at the time this was first measured, affecting `assessment_db` (41,431), `analytics_db` (10,389), `notification_db` (10,409), and `user_db` (1,747), with `auth_db` at 5. `resource_db`, `practice_db`, and `essay_db` had **zero** — never affected. **Updated during this file's thirteenth (final-confirmation) audit: re-counted and the total has grown to 67,607** — every affected pool's count is higher than before (`assessment_db` 43,823, `analytics_db` 10,968, `notification_db` 10,988, `user_db` 1,843, `auth_db` still 5). This is still actively accumulating, not a fixed historical count from a single incident. (The per-pool breakdown sums to within ~20 of the grep total — a minor log-parsing edge case in how pool names are extracted from a small number of lines, not worth chasing further; the scale and the fact that it keeps growing is the point, not the exact last digit.) **Caveat, not verified as certain:** the three heavily-affected services (`assessment`, `analytics`, `notification`) are exactly the ones that run their own dedicated Celery `-beat` container for periodic background tasks (confirmed via `docker ps`); `auth` and `practice` have no beat container at all, and `resource` has only a worker, no beat. This pattern fits "the unaffected pools are just queried far less often in the background, so they have fewer chances to hit a bad window" at least as well as it fits "those pools are somehow more reliable" — the near-zero count for `resource_db`/`practice_db`/`auth_db` should not be read as those connections being architecturally protected.
- **Still happening live, right now**: 371 warnings in the 5 minutes before this section was first written, and re-checked ~15 minutes later (during this file's eighth audit) at 748 warnings in the most recent 10 minutes — a steady ~75/minute both times, not tapering off.
- **Complication found during this file's eighth audit, weakening the "heavy local build activity" theory for this specific stretch:** the ~15 minutes between those two checks involved only this file's own light audit commands (`docker logs`, `docker inspect`, `grep`) — no builds, no test runs, nothing CPU-heavy. The failure rate held steady anyway. Today's *original* incident did correlate with a real `docker build` (see below), but this sustained, current stretch is failing at the same rate without one — meaning either something else is consuming this machine's resources in the background right now, independent of anything in this session, or heavy-local-load is not the only trigger.
- The volume is not constant — it's **clustered into bursts of hundreds to thousands within specific hours** (e.g. on 2026-09-18: 5 warnings at 01:00, but 4,390 at 17:00 and 4,153 at 22:00). This pattern looks like it correlates with active, heavy development sessions, not a fixed schedule or a one-time event.

What was directly, independently confirmed as a real application-level failure (not just a PgBouncer log line): `user-service` failed twice with `django.db.utils.OperationalError: server closed the connection unexpectedly` — once via a real API call, once from its own Django shell. `assessment-service`, `notification-service`, and `analytics-service` show **zero** application-level errors in their own logs despite their pools appearing constantly in PgBouncer's warnings — meaning those services are mostly riding out the underlying instability on their working connections, while a background rate of connection attempts keeps silently failing underneath them. That silent-failure rate is high enough, and has been sustained long enough, that it isn't a fluke.

"No data was lost" was verified only for essay-service's own rollback (confirmed zero partial rows written) — never checked for the other four affected services, since they never surfaced an application-level error to check.

**Not caused by essay-service** — this pattern predates essay-service's existence by days (warnings from 2026-09-15 onward), and the one real failure reproduced was via a call that never touches essay-service at all.

**Gap found during this file's third audit (2026-09-20) — the 64,062 warnings are not one uniform failure mode.** Breaking down PgBouncer's own "cached error" field:

| Cached error | Count | What it means |
|---|---|---|
| `connect failed` | 44,908 | A brand-new connection attempt to RDS was refused/failed outright |
| `connect timeout` | 16,441 | A brand-new connection attempt to RDS timed out |
| `server DNS lookup failed` | 2,935 | PgBouncer couldn't even resolve `spark-primary-db...rds.amazonaws.com` to an IP |

**This matters because the "Contributing Structural Weak Spot" section below (idle-timeout / NAT dropping a connection PgBouncer thinks is still good) only explains a connection that was already established going stale while idle.** It does not explain any of the three error types above — all three happen while establishing a brand-new connection, before an idle-timeout could ever be relevant. The one error actually reproduced as a real application failure (`server closed the connection unexpectedly`, on an in-use connection) is a good match for the idle-timeout theory — but it is a small fraction of the total warning volume, not representative of most of it. The proposed PgBouncer fix later in this file would only help with that one failure mode; it would do nothing for the ~96% of warnings that are failed-to-connect-at-all, including a genuine DNS resolution failure, which is a different problem (most likely a local network/DNS interruption, or the same network stack going unavailable during heavy load, rather than a tunable PgBouncer timeout).

**Checked and ruled out during this file's sixth audit — credentials are not the cause of the 64,062 warnings.** PgBouncer's logs do contain 40 `password authentication failed` entries, but every one of them is for `essay_db_user` specifically, timestamped 2026-09-19 ~10:12 UTC — that's the already-known, already-resolved issue from Phase 1 (`essay_db`/`essay_db_user` didn't exist on real RDS yet at that point; already fixed by moving essay-service to its own local Postgres substitute, see `LIVETRACKER3_V1.md`). None of the 64,062 warnings for `assessment_db`/`analytics_db`/`notification_db`/`user_db` show any authentication failure — confirming these are genuinely pre-authentication (network/TLS-level) failures, not a credentials problem, and are unrelated to the separate essay_db_user incident.

## Most Likely Root Cause

**Superseded during this file's ninth audit by a direct, conclusive, live reproduction — this is no longer a theory built from log patterns.**

Raw TCP connection attempts to the RDS endpoint (`spark-primary-db...rds.amazonaws.com:5432`) were made directly, right now, from two different, unrelated containers (`essay-service` and `user-service`, neither of which is PgBouncer): **8 out of 8 attempts timed out completely** (5–6 seconds each). The same container that failed to reach RDS connected to an unrelated external host (`8.8.8.8:443`, Google's public DNS) **instantly, in 0.12 seconds**, in the same test run.

**This rules out, conclusively, not just theoretically:**
- Local CPU/resource overload (already weakened by the earlier `docker stats` check; now directly contradicted — general connectivity works instantly).
- A general network or internet outage on this machine (proven by the instant success reaching an unrelated external host).
- General DNS failure (the hostname still resolves to a stable IP, confirmed earlier).

**Sharpened during this file's tenth audit, then refined further during the eleventh with more direct evidence.** At the moment a fresh TCP attempt timed out, `auth-service`'s own `/health/` endpoint still reported `"db": "ok"` — explained by `pool_mode = transaction` reusing already-open backend connections rather than opening a new one per health check. That reconciliation still holds in general. But a direct OS-level check inside the PgBouncer container itself (`netstat`), done immediately after, is more precise than inferring from a health check, and it painted a starker picture at that exact moment: **zero connections from PgBouncer to the real RDS IP in `ESTABLISHED` state, and three of PgBouncer's own outbound attempts stuck in `SYN_SENT`** (the connection request was sent; nothing ever answered). Also confirmed the same failure connecting directly by IP (`16.112.213.174:5432`), bypassing DNS entirely — a third independent method, same result.

**Correcting the previous framing rather than layering more confidence on it: "existing connections keep working" is not a stable, clean state — it fluctuates.** At the moment of the health check, something was apparently still reachable; moments later, a raw socket inspection found nothing established at all. The most defensible summary is: connectivity to this RDS instance from this environment is currently unreliable to the point of being mostly or entirely unavailable for new connections, with brief or partial exceptions, not a clean "old connections fine, new ones blocked" rule.

This also sharpens what's actionable: it is not that the RDS instance is fully down (a fully-down instance would also drop already-established connections, which isn't happening). It looks more specifically like **something is blocking new connection establishment while allowing already-open connections to continue** — the classic signature of a security group / network ACL change, or a stateful firewall's connection table treating new vs. established traffic differently. That is a much more specific, more checkable thing on the AWS side than "is RDS down."

**This materially changes the urgency framing of this whole file.** The original framing ("occasional flakiness under heavy local load, safe to defer") was reasonable given what was known at the time, but the picture that has actually emerged is: **this RDS instance currently rejects brand-new connections while still serving existing ones**, confirmed independently from two different containers, re-confirmed still true on a second check, with local causes conclusively ruled out. Given this instance also reportedly backs production, this is worth telling the user about directly and promptly — not just leaving in a deferred file — regardless of what they decide to do about it.

The local-overload theory still stands for the **one originally-investigated incident** (today's real `user-service` error, which did follow a CPU-heavy `docker build`) — that may have been a real, separate, resource-driven blip layered on top of this larger, ongoing connectivity problem. Both can be true at once. This dev machine's Docker Desktop is still only allocated **2 CPUs and 3.8GB RAM** for **25 containers**, which remains worth fixing regardless (see below), but it is not the explanation for what was just reproduced.

**Also checked during this file's fourth audit, to rule out an obvious alternative:** the RDS hostname (`spark-primary-db...rds.amazonaws.com`) was resolved three times just now and returned the same IP every time — no sign of an active DNS failover in progress right now. This doesn't rule out a failover having happened during one of the earlier historical burst windows (no way to check DNS resolution history from here), but there's no positive evidence for one either.

**Also checked, mostly ruled out (found during this file's fifth audit):** whether PgBouncer restarting itself explains the bursts — a restarting proxy can't serve any connection for the few seconds it takes to come back up. `docker logs infra-pgbouncer-1` shows exactly two restarts, both on 2026-09-19 (~08:20 and ~10:15 UTC), and the container has run continuously for the ~20 hours since (confirmed via `docker inspect`'s `StartedAt`). Large bursts still happened well inside that stable, non-restarting window — including today's 04:00–06:00 UTC one — so PgBouncer's own restarts are not the main driver of the volume, though they may explain isolated failures right around those two specific timestamps on the 19th.

**Checked during this file's seventh audit — found a real whole-stack restart event, but it does not explain the bursts either.** Every long-running container checked (11 of them: `nginx`, `redis`, `auth`, `assessment`, `user`, `analytics`, `notification`, `resource`, `practice`, `clamav`, plus PgBouncer's own second restart) started within the same second — `2026-09-19T08:20:17–18` — meaning the entire Docker stack was restarted together at that moment (most likely a Docker Desktop restart or a Windows sleep/wake/reboot; not distinguishable from container logs alone). This is a real, confirmed event, not a guess. But checking whether it correlates with a failure spike: it does not. The hour of the restart itself (08:00 UTC on the 19th) shows only 6 warnings — not elevated at all — while that same day's real burst (4,281 + 4,206 warnings) happened hours earlier, at 00:00–01:00, before anything restarted. A clean, orderly stack restart (services waiting on PgBouncer's own healthcheck via `docker-compose`'s `depends_on`) evidently does not itself trigger a login-failure storm. This event is recorded here for completeness, not as an explanation.

No AWS CLI/credentials are configured on this machine, so RDS's own CloudWatch metrics (connection count, CPU, network) could not be checked directly — this diagnosis is built entirely from local evidence (PgBouncer logs, config, Docker's own resource allocation, and the four affected services' own application logs). A genuine RDS-side cause (e.g. an intermittently saturated instance, a security-group/network path issue, a past failover) cannot be ruled out from here.

## Contributing Structural Weak Spot (secondary, independent of the trigger above)

`pgbouncer.ini`'s own comment confirms the connection to RDS travels the **public internet**, not a private AWS-only network. Current settings:

```ini
server_idle_timeout  = 600   ; 10 minutes
client_idle_timeout  = 60
```

**Correction (2026-09-20):** the first draft of this file said "no `tcp_keepalive` setting is configured" — more precisely, PgBouncer's `tcp_keepalive` defaults to on at the socket level even when unset, but the actual keepalive timing (`tcp_keepidle`/`tcp_keepintvl`/`tcp_keepcnt`) then falls back to the operating system's own defaults, which on Linux are typically ~2 hours — far too long to catch a router/NAT timeout measured in minutes. None of those three are set explicitly here, so the keepalive that is technically running isn't tuned to actually help with this. Home/office routers and ISPs often silently drop idle internet connections well under 10 minutes, without notifying either side. PgBouncer can then hand out a connection it still believes is healthy, only to discover it's dead when a real query tries to use it — producing this exact error, independent of any local machine overload.

## Proposed Solution (not applied — awaiting confirmation)

**Scoped honestly: this only addresses the reused-idle-connection failure mode (the one real application error actually reproduced), not the bulk of the 64,062 warnings (fresh-connection failures and DNS lookup failures — see the table above).** There is no proposed PgBouncer-config fix for those in this file, because they aren't PgBouncer config problems — they most likely trace back to the local machine/network being briefly unavailable, which a PgBouncer timeout setting can't prevent.

Edit `infra/pgbouncer/pgbouncer.ini`:
1. Lower `server_idle_timeout` from `600` to something safely under typical NAT/router idle timeouts — e.g. `120`.
2. Explicitly set `tcp_keepidle` (e.g. `60`) — and `tcp_keepintvl`/`tcp_keepcnt` if PgBouncer's version exposes them — so the already-on-by-default keepalive actually probes on a timescale short enough to matter, instead of inheriting the OS's ~2-hour default.

This is a config-only change to a local file — it does not touch AWS/RDS itself. It affects all services that go through PgBouncer (today: the 7 original services; essay-service once it eventually switches over).

**Additional, independent option (not a PgBouncer change at all):** increasing Docker Desktop's own CPU/memory allocation (Docker Desktop → Settings → Resources, currently 2 CPUs / 3.8GB for 25 containers) is a separate, simple thing worth trying — it would directly address the one confirmed local-overload incident (today's `docker build`-correlated failure). **Caveat added during this file's eighth audit:** given the live `docker stats` measurement above showing near-zero CPU usage during an active failure window, this change would likely **not** fix the currently-ongoing, unexplained background rate — that one appears to have a different, unidentified cause. Worth doing regardless (it's low-cost and helps the confirmed incident), just don't expect it to be a complete fix. Not applied — this is the user's own machine setting, not something to change unprompted.
