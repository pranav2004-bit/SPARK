## Non-Negotiable Constraints

1. **Zero regression on the existing 7 services + frontend.** `auth-service`, `user-service`, `resource-service`, `practice-service`, `notification-service`, `analytics-service`, `assessment-service`, and the Next.js frontend must build, deploy, and pass their existing test suites **unchanged** after every task in this tracker.
2. **New database, zero shared DB, zero cross-service FK.** `essay-service` owns `essay_db` exclusively (same PgBouncer instance, new per-service DB — mirrors every existing service). Student/batch/institution data is read via `user-service`'s API or the JWT's own claims, never via direct DB access.
   > **Temporary, explicitly consented exception (2026-09-19, see Task 1.2):** until the real `essay_db`/`essay_db_user` exist on RDS, `essay-service`/`essay-worker`/`essay-beat` bypass PgBouncer entirely and connect to a dedicated local-only `essay-postgres` container instead — a literal, temporary deviation from "same PgBouncer instance," approved by name, reversed before production, affecting no other service.
3. **Institution isolation is mandatory on every model and every query** — `institution_id` (from the JWT claim) filters every queryset, matching `practice-service`/`assessment-service` convention.
4. **Server is the sole source of truth for exam timing.** Reuse `assessment-service`'s already-built, already-load-tested pattern exactly (ADR 001 in that service — server-computed `ends_at`, Celery beat sweep auto-submit, server-time-sync endpoint for cosmetic client countdown). Do not re-derive this from scratch — see Task 0.1.
5. **No LLM call is ever made synchronously in a student-facing request.** Every evaluation happens in a Celery task, dispatched after submission, with the student already seeing "submitted" — this is non-negotiable for both UX (LLM latency is seconds, not milliseconds) and resilience (an LLM outage must never block or fail a student's submission).
6. **Full-Platform Regression Pass** = existing test suites for all 7 services + frontend `tsc`/`jest`/`next build`, run twice consecutively, zero failures. Required at the end of **every phase** in this tracker, not just at the end of the project.
7. **Shared files are additive-only.** Any shared file touched (`infra/docker-compose.dev.yml`, `infra/docker-compose.prod.yml`, `infra/scripts/validate-env.sh`, `gateway/nginx.conf`, `gateway/nginx.dev.conf`, `frontend/src/components/layout/AdminLayout.tsx`, `frontend/src/components/layout/StudentLayout.tsx`, `frontend/src/proxy.ts`, `frontend/src/lib/portalRouting.ts`) gets new blocks/entries appended — existing blocks are left byte-for-byte untouched unless a task explicitly says otherwise.
8. **The LLM's output is data, never an access-control decision.** A score/feedback string is stored and displayed; it never gates a permission check, never executes as code, never determines who can see what.
9. **Cost is a first-class constraint, not an afterthought.** Every LLM-calling task must state its retry ceiling and worst-case calls-per-submission before being marked complete (ties to ET11).

### Task 0.2 — LLM Evaluation Pipeline Architecture ADR

**Objective:** Decide the full LLM-calling design up front — provider, prompt shape, reliability posture, cost ceiling — before any pipeline code exists.

**Pre-empts:** ET1, ET5, ET11, ET15, Non-Negotiable Constraints §5, §9

- [x] Decide LLM provider/model and document why (cost, latency, JSON-mode reliability) — **Decided: OpenAI `gpt-4o-mini`**, JSON mode; upgrade to `gpt-4o` is the named revisit trigger if pilot quality is unacceptable, not a redesign
- [x] Design the evaluation prompt: **admin-defined rubric/prompt + the specific question + the student's response → strict JSON `{score: 0-10, feedback: {...}}`** — exact contract in the ADR, including what happens if the model returns malformed JSON
- [x] **Prompt-injection defense (ET1):** the essay text must be wrapped/delimited in the prompt such that it is unambiguously data, never instructions (e.g. a clearly-delimited block plus an explicit system instruction to disregard any instructions found inside the delimited student text); document the exact mitigation, don't just note the risk
- [x] PII redaction pass on the essay text before it leaves SPARK's infrastructure (reuse CLAP's pattern: email/phone/ID-like regex redaction), applied identically regardless of provider
- [x] Semantic-consistency guard: reject/retry an LLM response where the numeric score and the feedback text are self-contradictory (reuse CLAP's `_semantic_guard` concept)
- [x] Reliability posture: max retries, backoff policy, what counts as a permanent failure (→ DLQ) vs. a transient one (→ retry) — **Decided: 4 inline attempts, then DLQ; automatic sweeper adds up to 5 more after a 5-minute grace period before circuit-breaking** (9 calls worst-case per submission, sized against in the cost ceiling below)
- [x] **Quota tracker (fully verified from CLAP's `utils/quota_tracker.py`, not inferred)** — a real, reusable-as-is design: one atomic Redis Lua script checks and increments all four OpenAI quota dimensions (RPM/RPD/TPM/TPD) per key in a single round-trip (zero check-then-act race window), applies a 90% safety margin under the provider's real limit, hashes each key (SHA-256, never stores the raw key in Redis), and **fails OPEN specifically here** — if Redis is down, quota checks pass through rather than blocking evaluation. Note the deliberate asymmetry with Task 5.1's submission-rate-limiter, which fails CLOSED: quota-checking fails open because blocking a real evaluation on an unrelated Redis blip helps no one, while submission-creation fails closed because the harm of an unmetered flood (real API cost) is worse than briefly refusing new submissions. Copy this same reasoning, don't flatten both to one policy.
- [x] **Real numbers to size Task 0.4's capacity plan against:** CLAP's own defaults are `rpm_limit=3, rpd_limit=200, tpm_limit=60_000, tpd_limit=200_000` *per key* (Tier-1-shaped limits); the `QuotaTracker` applies its safety margin via `math.floor(rpm_limit * 0.90)`, giving exactly **2** effective requests/minute per key, not a fractional ~2.7 (an arithmetic error caught and fixed during this task's own audit pass — see ADR 004 Section 3 for the corrected drain-time table: 20 rotated keys → 40 effective RPM → ~50 minutes to drain 2,000, not the ~37 minutes first calculated). At a 2,000-submission exam, draining the evaluation queue in a reasonable window requires either (a) enough rotated keys that aggregate RPM is meaningful, (b) a higher-tier account with materially higher per-key limits, or (c) accepting and communicating a longer, explicit drain time to students/admins rather than assuming near-instant results. **Decided in the ADR: this platform has no OpenAI tier provisioned yet, so the real answer is deferred to a named blocking prerequisite (ADR 004 Section 3), not guessed at with CLAP's own account's numbers as if they were this platform's.**
- [x] **Cost ceiling (ET11):** worst-case LLM calls per submission (1 normal + N retries, capped), and a hard per-day/per-institution spend guardrail decision — **Decided: derive `QuotaTracker`'s own `tpd_limit` from an approved daily token/dollar budget rather than inventing a second ceiling mechanism**; new evaluations queue on `QuotaDailyExhaustedException`'s existing retry-to-next-day path rather than erroring, once hit
- [x] Idempotency: an evaluation task must never re-score a submission that already has a score (reuse CLAP's `SubmissionScore` existence check pattern)
- [x] Write `docs/adr/003-essay-llm-evaluation-pipeline.md` capturing all of the above

### Task 0.3 — Plagiarism / Text-Similarity Detection ADR (Scale-Aware)

**Objective:** CLAP's reference pattern (pairwise `difflib.SequenceMatcher` against every other completed student on the same test) is O(N²) and was never designed for a 2,000-concurrent target. Decide the actual scoped approach before building it.

**Pre-empts:** ET14

- [x] Decide the comparison **scope** — e.g. only within the same `EssayAssignment` + same assigned set/prompt variant (not platform-wide), which already bounds N to one batch's cohort rather than every student who ever took any essay test
- [x] **Precise complexity characterization (correcting an imprecise earlier statement in this ADR's first draft):** CLAP's own `check_text_similarity` docstring correctly calls each individual trigger **O(N)** — one newly-completed student compared against N already-completed peers, not N². The O(N²) concern is real, but only in **aggregate across a full cohort finishing**: student 2 checks against 1 prior, student 3 against 2, … student N against N-1 — summing to N(N-1)/2 total comparisons across the whole exam window. At a 2,000-student cohort that's ~2,000,000 total pairwise `difflib` comparisons spread across however long the exam window is, not 2,000,000 happening at one instant — state the actual expected time-spread of completions (an exam isn't 2,000 students finishing in the same second) before deciding this needs more than the scoping mitigation below
- [x] Decide whether pairwise comparison at the expected batch size (state the assumed batch size explicitly) is acceptable as-is, or whether a cheaper pre-filter (e.g. length-bucket or shingling/MinHash pre-check before the expensive pairwise pass) is needed to stay sub-second per newly-completed student — **Decided: no pre-filter for V1, revisit only if Task 5.4's real measurement shows a problem**
- [x] Decide the similarity threshold and whether it should vary by essay length (a short answer naturally has a higher baseline similarity than a long one — document the reasoning, don't just copy CLAP's flat 0.85) — **Decided: adopt 0.85 as the starting value but make it a configurable setting, not a hardcoded literal (CLAP hardcodes it)**
- [x] Document the decision and its numeric justification in `docs/adr/002-essay-service-architecture.md` (append, don't create a 4th ADR for this alone unless the decision is large enough to warrant it)
- **Testing:** Document review done. Back-of-envelope worst-case (~2,000,000 pairwise comparisons in aggregate across a full 2,000-student cohort, spread across the exam window, not instantaneous) is written into ADR 002 Decision 4.

- **Testing:** Concurrent-submit race test (genuine OS-thread concurrency, not sequential simulation — this exact class of test is what found a real bug in `assessment-service`; the same rigor here found a **real, different bug**, see below), duplicate-trigger test, idempotency-key collision test (covered by the OneToOneField + concurrency test together, since this design has no separate client-supplied key), Redis-outage-during-submission test (confirm it correctly rejects rather than floods — live-verified through the real `StudentEssaySubmitView` endpoint with a mocked Redis failure, 429 returned, attempt never finalized). **Real bug #1 found by the concurrency test itself:** if anything after the attempt-status UPDATE fails (a transient DB error during `EssaySubmission.bulk_create` or the malpractice update), the attempt is already irreversibly terminal but never gets a submission — and since candidate selection only ever looks for `IN_PROGRESS` rows, no future sweep or retry would ever discover or repair it, silently orphaning it forever. Fixed with `_repair_orphaned_submissions()`, run on every `finalize_attempts()` call (even ones that finalize nothing new), scoped to the caller's own queryset — self-healing on the very next sweep tick or retried submit. **Real bug #2, found immediately after fixing #1 (the fix's own added work increased lock contention enough to newly expose it):** DRF's `throttle.wait()` (called for every throttled/429 response) reads `self.history`, which the real `allow_request()` normally sets before returning — never reached when `FailClosedThrottleMixin`'s `RedisError` branch returns early. `ResilientThrottleMixin` never hit this (it always returns `True`, and DRF only calls `wait()` on a throttled request) — latent until the fail-closed mixin returned `False` for the first time. ### Task 5.2 — LLM Evaluation Task

### Post-18.2 follow-up, round 2 — full-service audit against the same bug class, plus the real 2,000-concurrent scalability gap

A direct audit request ("any gaps left, is this production-ready for 2,000 throughput") turned up two more real, previously-undiscovered issues by re-checking the actual code rather than trusting the round-1 writeup above:

**Gap A — 6 more `.delay()` call sites shared the identical unprotected-crash class the round-1 fix only closed in `scoring.py`.** A full grep of every `.delay()` in essay-service found `views.py`'s admin retrigger-evaluation view, score-override view, single/bulk report-resend views, the manual daily-summary view, `tasks.py`'s own `_transition_submission_status()` (the automatic report dispatch fired from inside `evaluate_essay` itself), `sweep_dlq_entries`'s own retry dispatch, and — most ironic — `sweep_undispatched_submissions` itself, the very recovery task built in round 1, had no protection around its own dispatch calls. Fixed with a new shared `core/celery_utils.py::safe_task_dispatch()` (mirrors `core/cache_utils.py`'s existing `safe_cache_*` pattern) instead of copy-pasting the same try/except 9 times. Each site got behavior matched to what it can safely do on failure: the retrigger view now reverts to `LLM_FAILED` (it had pre-set `LLM_PROCESSING`, a status `sweep_undispatched_submissions` never looks at, so an unhandled crash there would have left it stuck with no recovery path at all); the score-override view returns success (the override itself already committed) with a note that report generation will retry automatically; the bulk-resend view got the same circuit-breaker shape as the point below rather than crash-on-first-failure mid-loop; `sweep_dlq_entries` now only increments an entry's `dlq_retry_count` on an actual successful dispatch, not before attempting it. `sweep_undispatched_submissions` was also extended to scan for a second, related stuck state found in the same audit — `LLM_COMPLETE` with `report_html` still null past the grace period (the score-override view's own failure mode) — and redispatch `generate_essay_report` for those too.

**Gap B — the real one behind "2,000 at once": `_create_and_dispatch_submissions`'s dispatch loop had no bound, and every trigger (including the automatic mass-exam-expiry sweep) funnels through it.** Math, not assumption: at the live-measured ~1.5s per failed `.delay()` call, 2,000 simultaneous expirations during a genuine broker outage could have taken on the order of an hour for one `sweep_expired_attempts` tick to get through, tying up one of essay-worker's own limited concurrency slots (`--concurrency=2` in dev, `--concurrency=20` in prod) the entire time. Fixed with an in-process circuit breaker: the first broker failure in a batch sets a flag that skips every remaining `.delay()` attempt for the rest of that call — a broker outage is one shared condition, not N independent ones, so there's no reason to re-pay the same retry cost N times. Every `EssaySubmission` row is still created regardless (before dispatch is even attempted), so `sweep_undispatched_submissions` picks up everything skipped, a few minutes later, exactly as already proven in round 1. The healthy-broker case is entirely unaffected — nothing added any latency unless a real dispatch failure already occurred.

**A second, compounding bug was found live while verifying Gap B, not assumed fixed by the circuit breaker alone.** The dashboard-cache-invalidation loop that runs after every batch (`EssaySubmission.objects.filter(...).values_list("attempt__assignment_id", flat=True).distinct()`) was **not actually deduplicating** — confirmed live: a 30-attempt batch for one assignment produced the same assignment id 30 times, not once. Root cause: `EssaySubmission`'s own `Meta.ordering = ["-created_at"]` silently defeats `.distinct()` on Postgres (Django must fold the `ORDER BY` column into the `SELECT DISTINCT` list, and `created_at` differs per row even when `assignment_id` doesn't) — a well-known Django gotcha, not something introduced by this task. The same exact pattern existed in 3 places (`scoring.py`, `sweep_dlq_entries` in `tasks.py`, and an unrelated roster-batch lookup in `views.py`) — all three fixed the same way, an explicit `.order_by()` clearing the inherited ordering before `.distinct()`.

**Both fixes verified live together, not just reasoned about.** A 30-attempt batch during a full Redis outage: exactly 1 dispatch-failure log line and exactly 1 cache-invalidation-failure log line (both previously would have been N), task runtime 3.24s. A 200-attempt batch, same outage: still exactly 1 of each, task runtime 6.88s — confirming the Redis-outage-related cost is now flat (O(1)), not linear in batch size; the remaining growth (3.24s → 6.88s across a 6.7x larger batch) is ordinary database write work (200 `get_or_create` calls, the bulk status UPDATE, malpractice computation) that was never Redis-related and was never in this fix's scope — a fundamentally different, predictable, non-catastrophic category of "takes longer" than the unbounded outage-multiplied delay this fix actually targets. Extrapolating (not directly measured) to 2,000 attempts: the DB-proportional component would scale accordingly, but the Redis-outage risk that used to multiply by N no longer does.

### Post-18.2 follow-up — plagiarism checker's own similarity calculation was silently broken (2026-09-24)

Found while auditing the AI-response side of the pipeline (a separate direction from the Redis-dispatch work above), not the Redis-outage topic — kept here for chronological continuity with the rest of this session's own audit trail.

**`check_text_similarity` (essays/tasks.py) had a real, serious bug: `difflib.SequenceMatcher(None, my_text, peer_text)` used Python's own `autojunk=True` default**, which treats frequently-occurring characters as noise for any sequence longer than 200 characters — true of nearly every real essay. Confirmed live, not assumed: two essays sharing 3 of 5 sentences verbatim (a realistic "copy most of it, write my own intro/conclusion to disguise it" cheating pattern, not just a lazy full copy) scored **80% with autojunk correctly disabled, but only 1.1% with the buggy default** — meaning the checker was effectively non-functional in production for anything short of a complete, word-for-word, start-to-end copy (the one case unaffected, since fully identical text still scores 100% either way). This was never caught because the existing test suite (`test_plagiarism.py`) only ever tested the two extremes — fully identical and completely unrelated — never a realistic partial copy.

**Fixed** by passing `autojunk=False` explicitly, with a detailed inline comment explaining why (`autojunk`'s heuristic is meant for source-code diffing — long runs of common punctuation/whitespace — not natural-language prose, where common characters carry real signal). **Added the missing test class** (`TestPartialCopyMatch`) using the exact essays from the live reproduction, deliberately independent of whatever the production threshold is set to (`override_settings` in the test) so it specifically validates the ratio *calculation*, not a threshold policy choice.

**That bug also made the old `ESSAY_TEXT_SIMILARITY_THRESHOLD = 0.85` default stale** — it was whatever it was calibrated against buggy, near-zero ratios, not the now-correct ones. Re-derived empirically (not guessed): tested at two different essay lengths (~600 chars and a realistic ~500-word length matching this platform's own `word_limit`) and two different topics. Two honest students independently writing on the same topic consistently land ~20-30% (pure topical overlap, zero copying) at both lengths; a genuine partial copy (roughly 40% of a short essay's sentences copied verbatim) lands at 47-62% depending on length. **Changed the default to 0.60** — real margin above the honest-writing ceiling, while actually catching the realistic partial-copy pattern the old 0.85 (which needed 4-5 of 5 sentences copied before triggering at all) missed entirely. Updated in all three places this value lives: `core/settings.py` (the real, active default), `essays/tasks.py`'s own defensive fallback constant, and `.env.example`'s documentation.

**Honestly disclosed, not glossed over:** this number is re-derived from synthetic test essays I wrote (two topics, two lengths), not real student submissions from this platform, and it doesn't cover narrow/factual question types (where honest answers may naturally converge more, potentially raising that ~20-30% baseline). Framed explicitly as a strong, evidence-backed starting point to ship now, not a permanently-settled number — flagged for revisiting once real submission data exists, the same way real plagiarism-detection tools are continuously re-tuned rather than fixed once. A separate, real limitation also surfaced during this same testing and is **not** fixed by this threshold change: the algorithm is order-sensitive, so an essay copied in full but with paragraphs reordered scored only 42% in testing — this is a known, already-disclosed "V1, revisit later" scope decision in the code's own comments (chunk/shingle-based matching would catch this; whole-text sequence matching does not), not something today's fix addresses.

### Plagiarism checker — algorithm replaced after the autojunk fix caused a performance regression (2026-10-04)

The `autojunk=False` accuracy fix worked, but a 2,000-peer stress test showed the comparison took about 700 seconds, and a realistic 50-peer test showed about 480ms per comparison versus 25ms with the buggy default. The `quick_ratio()` pre-filter did not help, since every pair passed it. Replaced `difflib.SequenceMatcher` with word 5-gram containment (`_text_shingles` / `_shingle_containment` in `essays/tasks.py`). Live timing: 2,000 peers in 0.035s total. Threshold set to 0.30 from synthetic measurements: honest same-topic writing 0%, weak partial copy (2 of 5 sentences) 34%, stronger partial copy 62%, reordered full copy 79%. Tests updated (failure-injection patches retargeted to the new helper) and three default-threshold behavior tests added. Plagiarism suite 16/16; full backend suite passed twice. The threshold is a review trigger tuned on synthetic data, not a verified production value. The 0.60 / `SequenceMatcher` entries above are superseded by this one.
